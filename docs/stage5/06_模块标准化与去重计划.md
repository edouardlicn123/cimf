# Stage 5 — 模块标准化与去重计划

> 版本：v1.0 | 创建日期：2026-07-09 | 计划状态：待执行

---

## 一、背景与原则

经过 Stage 5 的 God 类拆分后，核心问题转向**模块代码质量不一致**和**可共享功能未充分提取**：

| 问题 | 现象 |
|------|------|
| 模型基类不一致 | whatsapp/clock 使用 `models.Model`，customer 使用 `BaseModel` |
| Service 设计不一致 | `BaseService` 已提供 CRUD，但 `TemplateService`/`CustomerService` 各自重复实现 |
| 工具函数未统一 | 4 个模块各写各的 `JsonResponse`、`try: int(...)` |
| 死代码残留 | `VersionService` 5 个无用方法、`LogService` 7 个未接入方法、`SampleDataService` 无调用 |
| 健康检查模式未共享 | `check_health`/`test_connection` 90% 重复 |

### 核心原则

```
多模块共用 → 移入 core/（共享基类、工具、mixin）
模块特有   → 精简后留在模块内（只保留业务逻辑）
```

```
批次 A（模型统一） ─→ ruff check + makemigrations ─┐
                                                    ↓
批次 B（Service 继承） ─→ ruff check ───────────────→ ────→ ruff check + manage.py check
                                                    ↑
批次 C（工具统一） ────→ ruff check ─────────────────┘
                                                    ↓
批次 D（标准化） ──────→ ruff check ───────────────→ 最终验证
                                                    ↓
批次 E（死代码） ──────→ ruff check ───────────────→ 最终验证
```

## 五、风险矩阵

| 风险项 | 级别 | 缓解措施 |
|--------|:----:|---------|
| `BaseModel` 迁移导致数据丢失 | 🔴 | `makemigrations` 时确认 `--name`，先 `--fake-initial` 测试 |
